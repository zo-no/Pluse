# 0016 — 滚动式 Progress Cycle 与聊天修正规划

**状态**: draft
**类型**: requirement
**优先级**: medium

## 背景

Pluse 当前已经有 Quest 级 Progress，Agent 也开始通过 CLI 主动创建和更新步骤。

但现阶段的 Progress 还存在几个明显问题：

- **粒度容易过细**
  - Agent 会把搜索、读文件、改单个函数、跑一条命令这类微动作写成独立步骤
  - 用户看到的是施工日志，而不是任务推进脉络

- **缺少“规划一轮、执行一轮、再判断下一轮”的节奏**
  - 现在更像一条不断追加的长列表
  - 缺少“本轮计划已走完，但任务还没结束，所以开启下一轮规划”的稳定语义

- **用户通过聊天修正计划时，没有明确的系统承接**
  - 用户说“先别做测试，先改 prompt”或“这里再补一步验证”
  - 这些输入应该被视为 Progress 计划修正，而不是普通聊天噪音

- **完成一个步骤后，缺少显式的任务完成判断**
  - Agent 现在会更新步骤状态，但不一定会在每一步后认真判断“整个任务是不是已经完成”
  - 这会导致 Progress 继续惯性推进，或者计划写完了但任务还没收口

## 真实问题

当前需要解决的核心问题不是“能不能看到更多 Progress”，而是：

**Pluse 应该如何让 Agent 用更合适的粒度规划任务，并以可滚动、可修正的周期方式推进一个 Quest。**

这里的关键不是隐藏信息，而是定义更好的 Progress 语义：

- 一次任务推进应该先形成一轮中层计划
- 执行中允许逐步实现
- 每完成一步都要重新判断任务是否结束
- 如果没结束，可以自然开启下一轮计划
- 用户在聊天中的修正，要能稳定地作用到当前或下一轮计划

## 顶层目标

Pluse 需要把 Quest 级 Progress 从“单条无限增长的步骤流”提升为“滚动式 Progress Cycle”。

理想状态下，一次任务推进应具有以下结构：

1. Agent 先创建一轮 Progress Cycle
2. Cycle 内默认包含 `2～4` 个中层步骤；复杂任务可扩展到更多，但要避免用户信息爆炸
3. Agent 逐步执行，每次只推进一个当前步骤
4. 每完成一步，都重新判断任务是否已经结束
5. 若当前 Cycle 完成但任务未结束，则开启下一轮 Cycle
6. 用户可通过聊天修正当前或后续计划

## 核心需求

### 1. Progress 需要有“轮次”语义

一次任务推进不应只是一串无限追加的条目，而应按“规划批次 / 推进轮次”组织。

用户看到的仍然可以是完整 Progress 历史，但系统内部需要知道：

- 哪些步骤属于同一轮计划
- 当前活跃的是哪一轮
- 某一轮是完成了、被替换了，还是取消了

### 2. Agent 创建 Progress 时应默认使用中层粒度

Progress 的默认单位应是“用户可理解的阶段目标”，而不是执行微动作。

例如应优先写：

- 梳理现有实现与约束
- 调整 Prompt 与规划规则
- 补充测试并验证

而不是：

- 搜索 `system-prompt.ts`
- 修改第 2 条断言
- 运行一次 `bun test`

### 3. 一次 Cycle 需要体现长程规划，而不是一步一想

Agent 在进入一轮新任务时，不应只创建一个当前步骤，再做完一步想下一步。

它需要先给出一轮较稳定的中层计划，让用户看到：

- 当前大概在做哪几段
- 后面还有哪几段
- Agent 不是边做边临时找方向

这并不要求一开始把所有细节拆完，但至少要有一轮 `2～4` 个中层阶段的前瞻计划；复杂任务可以更多，但要控制信息密度。

### 4. 每完成一步，都要显式判断“任务是否已完成”

步骤完成不等于任务完成。

Agent 在每个 Progress 条目标记为 `done` 后，都需要重新判断：

- 整个任务是否已经满足用户目标
- 如果未满足，是继续当前 Cycle 的下一个步骤
- 还是当前 Cycle 已经走完，需要开启下一轮计划

### 5. 用户聊天消息需要能修正 Progress 计划

用户对计划的修正应被视为正式输入，而不是普通补充对话。

至少应支持以下几类修正：

- 调整当前 Cycle 的步骤顺序
- 在当前 Cycle 中插入新步骤
- 删除或合并未来步骤
- 结束当前 Cycle，转入新的计划方向

### 6. 全量历史应保留，但当前推进语义要清晰

用户可以看到全部 Progress 内容，但系统需要让“当前正在推进哪一轮、哪一步、后面还剩什么”足够明确。

这意味着：

- 历史可以保留
- 但当前活跃 Cycle 必须清晰可辨
- 被替换的旧计划不应和当前计划混成一团

## 成功状态

如果这个需求成立，用户应能感受到：

- Progress 不再像一串细碎操作日志，而更像一轮一轮推进的计划
- Agent 会先给出一个中层、可理解的阶段规划，再开始做事
- 每做完一步，Agent 会重新判断任务是否已经完成
- 自然完成时默认用结果回复收口，不额外制造低价值 Todo / Progress / Reminder / Check-in
- 用户在聊天里改计划，Agent 会把这些修正吸收到当前或下一轮 Progress 中
- 任务变长时，Progress 会自然进入下一轮规划，而不是无限堆叠在一条列表里

## 不在范围内

这份 requirement 当前不规定：

- 是否一定要新建独立 `ProgressItem` 表
- 是否必须引入复杂层级结构（如树状子步骤）
- 多 Agent 并行协作下的联合计划
- 跨 Quest / 跨 Project 的总计划视图
- 自动评估“最佳计划”的算法
- UI 的最终视觉风格细节

这些内容属于后续 design 再讨论。
