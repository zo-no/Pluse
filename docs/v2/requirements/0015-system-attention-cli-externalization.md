# 0015 — 系统级注意力能力外置化

**状态**: draft
**类型**: requirement
**优先级**: medium

## 背景

Pluse 当前已经有 Quest、Run、Todo、Hook 等系统能力，也已经允许通过 hook 的 `shell` action 调用外部命令。

随着提醒、语音播报、桌面通知这类需求出现，一个边界问题越来越明显：

- 这些能力往往依赖具体操作系统
- 它们的实现方式会随着环境变化而变化
- 它们不只服务于 Pluse，也可能服务于 Claude Code、个人脚本或其他 Agent 项目

如果把这类能力直接做进 Pluse 本体，Pluse 就会开始承接大量系统实现细节，例如：

- macOS Reminders / Shortcuts / EventKit 的差异
- 系统权限申请与失败处理
- 提醒删除、完成、同步异常等平台行为
- 不同机器、不同用户环境的兼容问题

这会让产品边界变得混乱：Pluse 原本是 Agent 协作工作台，却逐渐变成某个操作系统的提醒实现层。

## 真实问题

当前需要解决的核心问题不是“要不要再做一个 Reminder 功能”，而是：

**Pluse 应该如何使用系统级注意力能力，而不把这类能力固化到自身内核里。**

如果这个边界不先锁定，后续会持续出现几类问题：

1. **产品语义和系统实现耦合**
   - Pluse 本应负责 Quest、Run、Todo、Check-in 这类协作语义
   - 但提醒弹窗、系统播报、原生提醒删除等属于 OS 集成细节
   - 两者混在一起后，产品对象会不断吸收不该承接的状态

2. **能力复用范围过窄**
   - 如果提醒能力只存在于 Pluse 内部，其他项目无法直接复用
   - 例如 Claude Code、个人自动化脚本、独立 Agent 项目仍然需要重复造轮子

3. **平台变更成本过高**
   - 今天可能是 macOS Reminders，明天可能是 Shortcuts、EventKit、语音播报或别的本地能力
   - 如果 Pluse 直接依赖某一种实现，每次切换都要修改产品核心逻辑

4. **系统级失败会污染产品核心**
   - 权限未开、系统 API 不稳定、快捷指令不存在、提醒列表被用户手工改动
   - 这些都属于外部系统问题，不应把 Pluse 核心状态机拖得更复杂

## 顶层目标

Pluse 需要把“系统级注意力能力”从产品内核中外置出去，收敛为一个独立 CLI 项目。

这个方向的目标是：

- Pluse 只负责决定何时触发、传递哪些上下文
- 独立 CLI 负责把抽象动作落到具体操作系统能力
- 同一个 CLI 可以被 Pluse 之外的项目复用
- Pluse 与 macOS 具体提醒实现保持解耦

## 核心需求

### 1. Pluse 只承接协作语义，不承接系统提醒实现

Pluse 需要继续承接的是：

- Quest / Run / Todo / Check-in 等产品对象
- Hook 触发时机
- Agent 可用的上下文
- 自动化与人工协作闭环

Pluse 不应默认承接的是：

- 原生提醒对象生命周期
- 桌面通知实现细节
- 语音播报引擎实现
- 系统权限、系统同步、系统兼容层

### 2. 系统级能力需要有独立、可复用的项目边界

提醒、播报、通知等系统能力需要存在于独立项目中，而不是埋在 Pluse 私有实现里。

这个独立项目至少要满足：

- 能被 Pluse 调用
- 能被其他 Agent 项目调用
- 不要求调用方理解具体平台实现
- 可以独立演进、替换和维护

### 3. Pluse 与外部能力之间需要稳定契约

Pluse 不应该面向 “macOS Reminders” 或 “某个快捷指令名字” 编程，而应该面向更稳定的抽象动作。

至少需要支持以下抽象能力：

- 创建一次系统提醒
- 删除或关闭一次系统提醒
- 触发一次语音播报或等价注意力动作

Pluse 需要依赖的是这层稳定契约，而不是某个具体 provider。

### 4. Hook 是默认接入桥，而不是把能力回收进内核

对于 Pluse 而言，最自然的接入点是现有 hooks / shell action 能力。

后续如果用户希望：

- Quest 完成后创建系统提醒
- 自动化失败后进行语音播报
- 某个项目触发高优先注意力动作

默认应通过 hook 调用外部 CLI 完成，而不是优先要求 Pluse 新增一套同类内建对象。

### 5. 产品语义与系统触达语义需要继续分层

不是所有当前“提醒”相关对象都应该一起外置。

例如：

- `Check-in` 更偏向“人类行为回执”和“事实记录”
- `Todo` 更偏向“人工承诺与执行事项”
- 系统提醒更偏向“触达用户注意力”

因此这份需求要先锁定的是“系统级触达能力外置”，而不是把所有产品内对象都外包给操作系统。

## 成功状态

如果这个需求成立，用户应能感受到：

- Pluse 不再因为系统提醒能力而不断膨胀内核边界
- 系统提醒、播报、通知可以作为独立 CLI 被多个项目复用
- Pluse 触发外部系统能力时，更多像在调用一个工具，而不是维护一个 OS 子系统
- 切换 macOS provider 时，不需要重写 Pluse 的产品语义
- `Todo`、`Check-in`、系统提醒三者边界更清晰，不再互相吸收

## 不在范围内

这份 requirement 当前不规定：

- 独立 CLI 的具体项目名
- 是否优先使用 Shortcuts、Reminders、EventKit 或其他 macOS provider
- CLI 的具体参数格式
- 是否记录外部提醒的引用 ID
- Hook 配置 UI 形态
- Check-in 是否也应外置
- 具体代码结构、数据库字段或 API 命名

这些内容属于后续 design 再讨论。
